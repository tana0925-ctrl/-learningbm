# ⚠ 2027年7月14日より前に必ず直すこと — 夏フェスのD1読み取り

**期限: 2027-07-14（`SUMMER26_START` の日付。ここを過ぎるとナビに夏フェスが出て、下の処理が動き出します）**

## 何が問題か

`GET /api/summer/status`（`src/index.tsx`）は、1回の呼び出しで **learning_results に対して5本のSQL**を実行します。
そのうち2本は **クラス全員の全履歴**を読みます。

概算で **1回あたり約14万行**（1クラス22人・1人3,000行のとき）。
`rateLimit(summer:<user>, 30, 60)` なので、1人が60秒に最大30回まで呼べます。

D1の無料枠は 1日500万行なので、**数人が夏フェス画面を開くだけで枯渇し得ます。**
2026年8月末にサイトが停止した件（`D1_ERROR: exceeded free tier daily row read limit`）でも、
これが相当効いていた可能性が高いと見ています。

## 原因は2つ

### 1. 日付の条件が索引を殺している

```sql
WHERE user_id = ? AND date(answered_at, '+9 hours') BETWEEN ? AND ?
```

`answered_at` に関数をかけているため、**期間の索引がまったく効きません**。
期間で絞っているつもりでも、その子（またはクラス全員）の全履歴を読んでから捨てています。

→ 素の比較に直す。`answered_at` は文字列なので、境界を UTC の文字列で作って
`answered_at >= ? AND answered_at < ?` の形にすれば索引が効きます。

### 2. クラス全員をスキャンする本数が多い

- 「クラス協力目標（花火）」の合計解答数
- 「週間ランキング」の集計

この2本が `JOIN class_members` でクラス全員ぶんを読みます。

→ 集計結果を1日1回だけ計算して保存する、または最低でも上の索引を効かせる。

## 直す場所

`src/index.tsx` の `app.get('/api/summer/status', ...)`（`SUMMER26_START` の定義のすぐ下）。
5本すべてが `date(answered_at, '+9 hours')` を使っています。

# 2027年4月をまたぐと壊れるもの：「今年度の積み上げ」が全期間になっている

`/api/teacher/student-full-analysis`（`src/index.tsx`）で、`homework_submissions` を読む
SQL には期間の条件が1つも付いていません。

```
SELECT day_key, todo, minutes, ... FROM homework_submissions WHERE user_id=? ORDER BY day_key DESC
```

ここから作っている `overview`（提出回数・合計時間・1日の平均・最長れんぞく・きもち☀%）と
`monthlyTrends` は、紙のカルテに「🌟 今年度の積み上げ」として印刷されます。
つまり **表示は「今年度」なのに、中身は「全期間」** です。

## いまは実害がない（2026-09-23 実測）

このアプリのデータは 2026-03-31 に始まっているため、「全期間」と「今年度」がほぼ一致します。

- `homework_submissions` … 全720件のうち、4月1日より前は **1件**（2026-03-31）
- `learning_results` … 4月1日より前は **2件**（2026-03）

## 2027年4月に実害が出る

年度が変わると、2026年度ぶんが丸ごと「今年度の積み上げ」に混ざります。
6年生は卒業するので影響は小さいですが、持ち上がる学年では
「今年度の最長れんぞく」が去年の記録になる、といったことが起きます。

## 直し方（1行）

`fyStartYMD()` は既にあるので、上のSQLに条件を足すだけです。

```
FROM homework_submissions WHERE user_id=? AND day_key >= ? ORDER BY day_key DESC
```

⚠ ただし `monthlyTrends`（月ごとの提出回数グラフ）と `maxStreak`（最長れんぞく）も
同じ配列から作っているので、グラフの見え方が変わります。先生に確認してから直すこと。

## 参考

- `learning_results`（教科別の正答率）は 2026-09-02 に今年度（4/1〜）へ限定済み
- `drill_sessions` も今年度に限定済み
- `student_records` / `student_test_scores` / `teacher_student_notes` は期間条件なしだが、
  これは意図的（4月からの材料をぜんぶ引き出しとして使うため）。
  二度ほめの防止は `karte_material_uses` の台帳でやっている（2026-09-23・KARTE_MATERIAL_V1）
